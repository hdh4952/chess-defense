## 1. 개요

체스판 위에서 벌어지는 타워 디펜스다. 플레이어는 8×8 보드의 아래쪽 7줄에 체스 기물을 사서 배치하고, 위쪽(8랭크)에서 쏟아져 내려오는 적이 보드 아래로 빠져나가지 못하게 막는다. 20웨이브를 버티면 승리, 체력 10이 0이 되면 패배다.

핵심 아이디어는 하나다 — **체스의 행마법을 그대로 공격 패턴으로 쓴다.**

폰은 전방 대각 두 칸만 때리고, 룩은 자기 파일과 랭크를 보드 끝까지 관통하며, 비숍은 대각선을, 나이트는 L자로 뛰어 착지 지점에서 폭발한다. 퀸은 8방향 라인 위 아군의 공격력을 곱한다. 즉 **"어디에 두는가"가 곧 "무엇을 때리는가"**이고, 체스를 아는 사람은 규칙 설명 없이 사거리를 읽을 수 있다.

이 아이디어에서 파생되는 게임의 실제 성격은 세 가지다.

- **차단이 없다.** 적은 기물을 통과하고 기물도 적을 막지 않는다. 코드 어디에도 충돌·차단 개념이 없다. 배치는 순수하게 **사거리 기하학 문제**다.
- **파일 커버리지가 1차 제약이다.** 적은 스폰된 파일을 그대로 직진하고 파일을 바꾸지 않는다. 스폰 파일이 균등 랜덤이므로, 방어가 비어 있는 파일로 나온 적은 아무 저항 없이 24초 만에 통과한다.
- **관통이 시너지를 만든다.** 룩의 랭크 공격은 자기 파일이 아닌 파일도 전부 관통한다. 여러 룩이 랭크를 공유하면 그 랭크가 8파일 전체를 때린다 — 파일별로 따로 계산한 화력 추정이 실제보다 항상 보수적인 이유다.

## 2. 게임 루프

### 2.1 보드와 좌표계

| 항목 | 값 | 출처 |
|---|---|---|
| 보드 | 8×8 = 64칸 | `config.ts:2` |
| 한 칸 | 80px 정사각형 | `config.ts:2` |
| 캔버스 | 640×640px 고정 (파생값) | `grid.ts:6-7` |
| 파일(열) | 0~7 = a~h | `types.ts:3-4` |
| 랭크(행) | 1~8 (8이 화면 최상단) | `grid.ts:10-12` |
| 배치 가능 영역 | 1~7랭크 = **56칸** | `pieces.ts:17-19` |
| 스폰 구역 | 8랭크 (배치 금지) | `pieces.ts:18` |

좌표 변환은 전부 한 함수씩만 존재한다. 이것이 이 코드베이스의 기본 태도다.

- `rankToTopY(rank) = (8 − rank) × 80` — 보드 그리기·하이라이트·기물 그리기가 전부 이 하나를 재사용한다.
- `yToRank(y)` — 보드 밖 값을 가장자리 랭크로 클램프한다(y < 0 → 랭크 8, y ≥ 640 → 랭크 1).
- `enemySquare(e)` — 적의 현재 칸 = **중심 좌표가 속한 칸**. 파일은 스폰 파일 그대로 고정이고 랭크만 y에서 계산한다. **모든 공격 범위 판정이 이 한 함수를 통과한다.**
- `fileLabel(file)` — 파일 인덱스 → a~h 라벨.

> **왜 중심 좌표 기준인가** — 적이 픽셀 단위로 연속 이동하기 때문이다. 판정 기준을 한 함수로 좁혀 두어야 공격 범위·이펙트·보스 비네트가 서로 다른 기준으로 갈라지지 않는다.

화면 좌표 → 칸 변환은 캔버스의 `getBoundingClientRect` 기준 **비율**로 계산하므로 CSS 확대/축소와 무관하게 동작한다.

### 2.2 페이즈

페이즈는 넷뿐이고, 전이도 다섯 개뿐이다.

```
        타이머 만료 / 수동 시작
prepare ──────────────────────> wave
   ^                             │
   └───── 웨이브 클리어 ──────────┤
                                 ├── 20웨이브 클리어 ──> victory ┐
                                 └── 체력 0 ──────────> defeat  ┤
                                                                │
                              location.reload() (다시 시작) <────┘
```

`victory`/`defeat`는 종단 상태다. 빠져나오는 유일한 경로는 결과 화면의 '다시 시작' = `location.reload()`이며, 자연히 시작 화면으로 되돌아간다.

### 2.3 1틱 처리 순서 — 순서 자체가 규칙이다

```
stepGame(state, dt, events, rng)
  0. paused || victory || defeat  →  즉시 반환
  1. updatePrepare   준비 타이머 카운트다운
  2. updateSpawning  적 스폰
  3. moveEnemies     적 위치 갱신
  4. updateCombat    쿨다운 → 공격 판정 → 처치/골드
  5. processLeaks    보드 통과 → 체력 감소
     ├─ 여기서 defeat가 되면 → 즉시 반환 (6번 실행 안 함)
  6. checkWaveEnd    웨이브 종료 / 승리 판정
```

이 순서에서 나오는 세 가지 결과는 전부 의도된 것이다.

| 순서 관계 | 결과 |
|---|---|
| 이동(3) < 전투(4) | 공격은 항상 **이번 틱 이동이 끝난 위치** 기준으로 판정된다 |
| 전투(4) < 누수(5) | 보드를 막 벗어난 적도 그 틱의 공격 대상이다 — **마지막 순간 처치가 실제로 인정된다** |
| 누수(5) < 종료 판정(6) | **체력 0은 웨이브 클리어/승리보다 항상 우선한다** |

체력이 0 이하가 되면 그 자리에서 `hp`를 0으로 고정하고 `phase`를 `defeat`로 바꾼 뒤 **그 틱의 남은 누수 처리를 즉시 중단한다.** 이미 진 뒤에 체력이 더 깎이거나 이벤트가 더 나가지 않게 하기 위해서다. 부작용으로, 같은 프레임에 보드를 벗어나던 나머지 적들은 소멸하지 않고 화면에 그대로 남는다 — **결과 화면 뒤에 적이 멈춰 있는 것은 의도된 동작이다**(`tests/enemy.test.ts:79-91`이 고정).

> **`step.ts`의 `state.phase as Phase` 캐스트를 지우지 말 것.** TypeScript는 `processLeaks` 호출이 내부에서 `phase`를 `'defeat'`로 바꿀 수 있다는 사실을 추적하지 못한다(객체 프로퍼티의 좁혀진 타입은 함수 호출을 지나도 자동 무효화되지 않는다). 캐스트 없이 비교하면 "두 타입이 겹치지 않는다"는 TS2367 컴파일 에러가 난다. 순수하게 컴파일러 설득용이고, 런타임에는 완전히 지워진다. "중복 검사처럼 보인다"며 지우면 에러가 재발한다.

### 2.4 웨이브 구조

| 항목 | 값 |
|---|---|
| 총 웨이브 | 20 |
| 준비 시간 | 10초 (카운트다운) |
| 스폰 간격 | 1.0초 |
| 클리어 보너스 | 300G 정액 |
| 보스 주기 | 5의 배수 웨이브 (5·10·15·20) |

**웨이브 시작** — 준비 타이머가 만료되거나 '웨이브 시작' 버튼을 누르면 시작한다. `startWave`가 `spawnTimer`를 0으로 두고 **같은 `stepGame` 호출 안에서** `updateSpawning`이 곧바로 실행되므로, **첫 적은 준비 종료와 같은 틱에 스폰된다.** 따라서 n마리 웨이브의 스폰 구간은 n초가 아니라 **(n−1)초**이고, 마지막 적은 t = (n−1)초에 나온다.

> **왜 조기 시작 보너스가 없는가** — 준비 시간을 "자원을 쥐고 기다릴지 말지"의 선택으로 남기기 위해서다. 보너스를 붙이면 항상 조기 시작이 정답이 되어 준비 페이즈가 형식만 남는다.

**웨이브 종료** — 조건은 "스폰이 전부 끝났고 **보드 위 생존 적이 0**"이다. 전멸이 아니라 '보드가 빔'으로 정의한 덕분에 처치와 누수를 같은 경로로 다룰 수 있고, 20웨이브 보스를 놓쳐도 승리로 이어지는 규칙이 별도 예외 없이 성립한다.

종료 시 클리어 보너스 300G를 지급하고, 20웨이브면 `victory`로, 아니면 웨이브를 1 올리고 `prepare`로 되돌리며 준비 타이머를 10초로 재설정한다.

### 2.5 승패 조건

| 조건 | 결과 |
|---|---|
| 20웨이브 클리어 | **승리** — 보너스 300G 지급 후 `victory` 전환 |
| 체력 0 이하 | **패배** — 즉시 `defeat`, 같은 틱 나머지 누수 처리 중단 |

시작 체력 10, 회복 수단 없음. **게임 전체에서 일반 적 9마리까지 통과 가능**하고 10마리째에 패배한다. 보스는 1회만 통과 가능하고 2회째에 패배한다.

> **20웨이브 보스를 놓쳤을 때의 경계는 체력 6이다.** 체력 6 이상이면 −5 후 웨이브가 종료되어 승리, 체력 5 이하면 누수 처리에서 `defeat`가 먼저 확정되고 `checkWaveEnd`(승리 판정)는 아예 실행되지 않는다. "마지막 보스를 놓쳐도 이긴다"는 규칙에는 이 단서가 붙는다. (`tests/simulation.test.ts:132-153`이 실측 고정)

### 2.6 시간·일시정지·배속

| 항목 | 값 |
|---|---|
| 시뮬레이션 | 고정 스텝 1/60초 |
| 프레임당 실시간 소비 상한 | 0.25초 (최대 15스텝) |
| 배속 | 1x / 2x — `dt`에 곱해 `stepGame`에 전달 |

> **왜 고정 스텝인가** — rAF의 가변 프레임 시간이 그대로 `dt`가 되면 시뮬레이션이 프레임률에 따라 달라진다. 프레임당 소비 실시간을 0.25초로 자른 것은 탭 복귀 시 밀린 시간을 한꺼번에 재생해 "멈춤 후 급가속"이 나는 것을 막기 위해서다. 밀린 시간은 따라잡지 않고 **그냥 버린다** — 프레임이 4FPS 아래로 떨어지면 게임 시간이 실시간보다 조용히 느려진다.

> **왜 배속을 `dt`에 곱하는가** — 단일 지점(`main.ts`)에서 곱하는 덕분에 코어 규칙 어디에도 배속 분기가 없다. 준비 시간·스폰 간격·적 이동·기물 쿨다운이 자동으로 같은 비율을 탄다. **게임 규칙은 배속을 전혀 인지하지 않는다.**

**일시정지** — 버튼 토글이며 `victory`/`defeat`에서는 무시된다. `stepGame`이 맨 앞에서 즉시 반환하므로 준비 타이머·스폰·이동·쿨다운·누수 어느 것도 진행되지 않는다. 탭이 백그라운드로 가면 `prepare`/`wave` 중에 한해 자동 일시정지되고, **자동 재개는 절대 하지 않는다.**

> **왜 자동 재개하지 않는가** — 복귀 즉시 게임이 돌아가면 플레이어가 상황을 파악하기 전에 적이 지나간다. 해제는 반드시 수동이다.

## 3. 적 시스템

### 3.1 이동

적은 스폰된 파일을 그대로 직진하며 **파일을 바꾸지 않는다.** 이동은 `y += speed × dt`의 연속 이동이다.

| 종류 | 칸당 체류 | 속도 | 보드 종주 |
|---|---|---|---|
| 일반 | 3.0초 | 80 / 3.0 ≈ **26.67 px/s** | **24.0초** |
| 보스 | 6.0초 | ×0.5 ≈ **13.33 px/s** | **48.0초** |

> **왜 보스가 느린가** — "한 마리에게 딜을 넣을 시간"을 늘려 주는 장치다. 대신 보스를 놓쳐도 웨이브는 클리어 처리되므로, 보스전은 "막지 못하면 끝"이 아니라 **"처치 보상 + 체력 5"를 건 도박**이 된다.

### 3.2 스폰

- 스폰 파일은 **매 마리 독립적으로 균등 랜덤**이다: `file = min(7, floor(rng() × 8))`. 파일 배분을 보정하는 로직은 없으므로 **한 파일에 몰릴 수 있다.**
- 웨이브당 파일 하나에 오는 적의 기댓값 = 적 수 ÷ 8 (w1 = 1.25마리, w19 = 5.75마리).
- 적 ID는 `e-{웨이브}-{스폰순번}`이다.

### 3.3 HP 곡선

```
적 1마리 체력 = w ≤ 10 :  10 + (w−1) × 1
                w ≥ 11 :  19 + (w−10) × 4
보스 체력     = 그 값 × 30
```

| 웨이브 | 1 | 5 | 9 | 10 | **11** | 15 | 19 | 20 |
|---|---|---|---|---|---|---|---|---|
| 개체 HP | 10 | 14 | 18 | 19 | **23** | 39 | 55 | 59 |

**웨이브 11이 진짜 난이도 절벽이다.** 증가폭이 1에서 4로 뛰고, 적 수도 26 → 30으로 함께 뛴다.

> **주의** — `hpScalingBreakpoint`는 10이지만 **웨이브 10은 보스 웨이브라 일반 적이 없다.** 즉 +1 증가폭이 실제로 적용되는 마지막 일반 웨이브는 **w9(HP 18)**이고, 플레이어가 체감하는 난이도 계단은 w9(18) → w11(23)의 **+5**다.

### 3.4 적 수

```
적 수 = 5의 배수 웨이브면 1 (보스 단독), 아니면 10 + 2 × (w−1)
```

보스 웨이브에는 일반 적이 섞이지 않는다. 20웨이브 총 적 수 = **452마리** (일반 448 + 보스 4).

### 3.5 보스

| 항목 | 값 |
|---|---|
| 체력 | 같은 웨이브 일반 적 HP × 30 |
| 속도 | ×0.5 |
| 누수 피해 | −5 |
| 등장 | w5 (420) · w10 (570) · w15 (1,170) · w20 (1,770) |

별도 체력 테이블이 없고 전부 `enemyHp(w)`에서 유도된다. 보스 4마리 체력 합 = 3,930.

**보스 연출은 3단이다.**

1. 준비 중 배너 `⚠ BOSS WAVE` + HUD 보스 아이콘 상시 표시
2. 스폰 시 해당 파일 전체 1초 붉은 강조(`rgba(220,50,40,0.28)`, `main.ts:122-126`) + `♚ 보스 등장 — {파일}파일!` 배너
3. 보스가 2랭크에 진입하면(y ≥ 480) 화면 가장자리 붉은 비네트

### 3.6 누수

- 판정: 적의 **중심 y가 보드 하단(640px)에 도달하거나 넘었을 때** (`e.y >= BOARD_H`).
- 누수한 적은 소멸하고, 플레이어 체력이 일반 **−1** / 보스 **−5** 줄어든다.
- **누수한 적은 골드를 한 푼도 주지 않는다.**

> **주의** — `yToRank`가 보드 밖을 클램프하기 때문에, y ≥ 640이 되어 이미 '통과한' 적도 누수 처리 전까지는 랭크 1의 적으로 판정된다. 틱 순서상 전투가 누수보다 앞이므로 **이 적은 정확히 한 틱 동안 여전히 공격 대상이다.**

### 3.7 렌더 관련 규칙

- 적 스프라이트는 44px, 체력바는 상시 표시(40×4px, 중심 −30px).
- 렌더 시 파일 중심에서 **±8px의 지터**가 가로로 더해진다. 지터는 **적 ID의 해시로 결정**되므로 매 판 같은 웨이브·같은 순번의 적은 항상 같은 오프셋을 갖는다 — 무작위가 아니다.

> **왜 결정론적 지터인가** — 렌더에 흔들림을 주면서도 시뮬레이션 재현성을 깨지 않기 위해서다. 지터는 렌더 전용 값이라 **칸 판정에는 절대 들어가지 않는다.** 스프라이트 44px + 지터 8px = 중심에서 최대 30px이므로 80px 칸 경계(40px)를 절대 넘지 않는다.

- 적 스프라이트는 y 오름차순으로 그려, 아래쪽(플레이어에 가까운) 적이 위에 겹친다.
- 적의 중심이 y좌표이므로 스폰 직후(y=0)에는 위쪽 절반이 보드 밖에 그려지고, 체력바는 화면에서 잘린다.

**수치의 출처와 그 예외**

비용·기본 공격력·공격 주기·공격당 골드는 `CONFIG.pieces` 한 곳에서만 정의되고, 툴팁·시작 화면·사거리 그림도 이 값과 `patterns.ts`에서 파생시킨다 — 밸런스를 바꾸면 설명이 함께 따라온다. **다만 예외가 둘 있고, 둘 다 퀸에 몰려 있다.**

1. **퀸 버프의 크기는 `CONFIG`에 아예 없다.** `buff.ts:22`의 `p.queenBuffCount += tierMultiplier(q.tier)`가 유일한 정의이며, 기준값 +1(= `tierMultiplier(1)`)을 조정할 노브가 `config.ts` 어디에도 없다. 밸런스를 바꾸려면 `buff.ts`를 고쳐야 한다(§10.5 표에 등재).
2. **시작 화면의 퀸 산문은 여전히 하드코딩이다.** 툴팁은 `버프 효과: +${tierMultiplier(p.tier) * 100}%`로 파생되도록 고쳤지만(퀸 상한 변경과 함께, §12.8), `titleScreen.ts`의 퀸 산문("공격력을 두 배로 올리며")은 코드에서 유도되지 않아 기준값을 바꾸면 따라오지 않는다. 수치 dl은 따라온다.

### 4.2 공통 전투 규칙

**최종 공격력 = 기본 공격력 × 2^(강화단계−1) × (1 + 자신을 비추는 퀸 버프 합)** — 세 항 전부 곱셈이다.

- 공격은 **사거리 칸 목록 전체에 동시에 적용된다.** 한 칸에 겹친 여러 적도, 여러 칸에 흩어진 적도 모두 같은 피해를 받는다 — **단일 표적 개념이 없다.**
- **광선은 완전 관통이다.** 아군 기물도 적도 사거리를 막지 못하고 보드 끝까지 뻗는다.
- **사거리 안에 적이 하나도 없으면 발사하지 않고** 쿨다운 0에서 대기한다. 적이 들어오는 즉시 발사한다(허공 발사 없음). 쿨다운은 **실제로 발사했을 때만** `interval`로 재시작한다.
- 기본 공격력이 0인 기물(현재 퀸)과 나이트는 주기 공격 루프에서 **통째로 제외된다.**
- **쿨다운은 칸이 아니라 기물 ID에 묶여 있다.** 슬롯(트레이)에 있어도 계속 흐르지만, 슬롯에서는 **발사하지 않는다**(발사 조건은 '보드 위 + 쿨다운 0').

> **왜 쿨다운이 기물 ID에 묶여 있는가** — 회수→재배치나 잦은 이동으로 쿨다운을 우회하는 파밍을 막기 위해서다. 나이트만은 사용자가 명시적으로 승인해 이 조항을 폐기했다(`interval: 0`).

> **쿨다운 스냅** — `dt`를 매 틱 반복해 빼면 반올림 오차(~1e-16)가 남아 쿨다운이 정확히 0에 도달하지 못한다. 1e-9 미만이면 0으로 스냅한다. 지우면 발사가 한 틱씩 밀린다.

- 적이 속한 칸 = **적 스프라이트 중심 y가 속한 칸**. 적과 기물은 **같은 칸에 겹쳐 존재할 수 있다**(충돌·차단 개념 없음).
- **8랭크는 배치 금지일 뿐 무적 구역이 아니다** — 룩·비숍·나이트·랭크7 폰 모두 스폰 직후의 적을 정상적으로 때린다.

### 4.3 폰 — 100G / 공격력 2 / 0.5초

**공격 범위: `(f−1, r+1)`, `(f+1, r+1)` 두 칸.**

자기 칸도, 자기 파일도 포함하지 않는다. **폰은 자신이 선 파일로 내려오는 적을 절대 때리지 못한다.**

0.5초 주기로 이론 DPS 4.00 — 전 기물 중 최고이고 100G당 4.00 dps로 골드 효율도 최고다. 그러나 커버가 2칸뿐이라 적 1마리에게 넣는 총딜은 12에 그친다. **속사 기물이지만 노출 시간이 짧다**는 것이 폰의 성격 전체를 결정한다.

> **기하학적 상한** — 한 칸을 동시에 타격할 수 있는 폰은 **최대 2기**다. 보스 파일 좌우 인접 2기만 유효하고, 세 번째 폰은 아무리 완벽히 추격해도 기여가 **정확히 0**이다(실측, `tests/simulation.test.ts:155-192`). 재조정에도 불변인 기하학적 사실이다.

### 4.4 나이트 — 300G / 공격력 3 / 폭발형

**폭발 범위: 자기 칸을 포함한 주변 3×3 (최대 9칸).**

주기 공격이 **아예 없다.** `updateCombat`이 `p.type === 'knight'`로 하드 제외하므로, `interval`을 0이 아닌 값으로 되돌려도 주기 공격이 생기지는 않는다. 대신 **배치·이동할 때마다 폭발한다.**

폭발이 일어나는 지점은 정확히 셋이다.

1. 슬롯 → 보드 **배치** 직후
2. 보드 위 **L자 이동** 직후
3. **합성** 커밋 직후 (생존자 기준, 갱신된 티어의 공격력으로)

각 경우 정확히 1회다. 폭발은 **폭발 시점의 버프 상태**로 계산된다 — 배치/이동 직후 `recalcQueenBuffs`가 끝난 다음에 폭발한다.

**이동 제약** — 보드 위 나이트는 **L자 행마로만** 이동할 수 있고, 쿨다운이 남아 있으면 이동 자체가 거부된다. 현재 `interval`이 0이라 실질 무제한이다.

| 위치 | L자 이동 후보 칸 |
|---|---:|
| 중앙 (d4) | 8 |
| 랭크 7 (d7) | **4** |
| 모서리 (a1) | 2 |

(8랭크 착지 금지가 `knightMoves` 패턴 계산 단계에서 한 번, `resolveLanding`의 착지 판정에서 또 한 번 걸린다. 랭크 7에서 후보가 4개뿐인 것은 8개 중 rank > 8로 2개, 8랭크 필터로 2개가 빠지기 때문이다.)

> **L자 게이트는 합성에도 그대로 걸린다** — 게이트 순서상 `knightPattern` 검사가 합성 분기보다 앞이므로, **보드 위 나이트끼리는 L자 거리에서만 합쳐진다.** 인접 칸에 나란히 선 같은 티어 나이트 둘은 드래그해도 `knightPattern` 거부(원위치 복귀 + `uiInvalid`)다. 트레이발 나이트에는 이 게이트가 적용되지 않는다(§5.7).

> **쿨다운 게이트는 살아 있는 죽은 코드다** — `canLandAt` / `tryKnightBlast` / 합성 시 점유자 쿨다운 검사가 코드에 전부 남아 있다. `CONFIG.pieces.knight.interval`을 3.0 등으로 되돌리면 **코드 변경 없이** 옛 동작이 복원되고, 툴팁·시작 화면 문구도 자동으로 따라 복원된다.

**현재 상태의 귀결** — `interval`이 0이라 회수→재배치만 반복해도 폭발이 무제한 반복된다(승인된 규칙 변경). 나이트는 **골드당 성능을 dps로 표현할 수 없는 유일한 기물**이다 — 실질 화력이 플레이어의 조작 빈도에 비례한다(수치는 §9.2).

### 4.5 비숍 — 200G / 공격력 1 / 3.0초 / **공격당 +10G**

**공격 범위: 자기 칸 + 대각 4방향 끝까지** (8~14칸, 중앙 d4/e4/d5/e5가 14).

**유일한 골드 생산 기물**이다. v1.7에서 딜러(공격력 3)에서 경제 기물로 역할이 바뀌었다.

골드는 **'발사 1회'에 묶인 정액 보상**이다.

- 명중한 적 수도, 처치한 수도 무관하다 — 사거리에 적이 하나든 다섯이든 10G.
- **사거리에 적이 없으면 발사 자체가 없어 골드도 없다.**
- 강화 단계는 곱하지만 **퀸 버프는 곱하지 않는다.**
- 지급 지점은 `updateCombat` 안이지 `applyAttack`이 아니다.

> **왜 지급 지점이 `updateCombat`인가** — `applyAttack`은 나이트 폭발과 공유되는 "피해 적용" 함수이고, 골드는 피해나 처치가 아니라 **발사 1회**에 묶인 보상이기 때문이다.

> **왜 발사 횟수에 묶었는가** — 적이 사거리에 살아 있어야만 벌리는 구조라 **방어가 무너지면 수입도 함께 끊긴다.** 스노우볼을 구조적으로 막는 설계다.

> **왜 비용을 300 → 200으로 내렸는가** — 총 수익(`goldPerAttack`)을 올리면 이미 골드가 남아도는 후반 수입까지 부풀기 때문이다. 회수 시점만 앞당기려고 비용 쪽을 건드렸다. 목표는 **"초반에 지르고 굴린다"는 결정 자체가 성립하게** 만드는 것.

**회수 성능** (헤드리스 실측, 2026-08-15, 20웨이브 완주 ≈970초 — `config.ts:34-38`)

| 항목 | 값 |
|---|---|
| 회수 지점 | 200G ÷ 10G = 발사 20회 = 최소 60초 연속 사격 |
| 한 판 총 발사 | 112~185회 → **1,120~1,850G** (비용의 5.6~9.3배) |
| 웨이브당 수입 | 초반 20~60G → 후반 160~190G |
| **보스 웨이브** | **20~50G** (보스 1마리가 대각선을 잠깐 스칠 뿐) |

**이 곡선은 §9.1 골드 표에 들어 있지 않다.** 발사 횟수는 배치와 적 체류 시간에 좌우되므로 config만으로 유도할 수 없기 때문이다 — §6.1·§6.4·§9.1의 모든 골드 합계는 **비숍 0기 기준**이다.

**비숍은 후반 캐리 기물이 아니라 초반 투자 기물이다.** 수입 자체는 늘지만(20~60G → 160~190G) 후반 처치 골드가 웨이브당 2,000G를 넘으므로 비중은 오히려 줄어든다.

### 4.6 룩 — 500G / 공격력 5 / 3.0초

**공격 범위: 자기 칸 + 상하좌우 4방향 끝까지 — 보드 어디에 서든 항상 15칸.**

주력 딜러다. 자기 파일로 내려오는 적에게 종주 중 8~9발 = **40~45 피해**를 확정적으로 넣는다.

**관통 시너지** — 룩의 랭크 공격은 자기 파일이 아닌 파일도 전부 관통한다. 여러 룩이 같은 랭크를 공유하면 **그 랭크가 8파일 전체를 관통 타격한다.**

> **비둘기집 원리** — 파일은 8개인데 배치 가능 랭크는 7개뿐이라, '파일당 룩 1개' 배치는 어떤 랭크를 고르든 **최소 한 랭크는 반드시 공유된다.** 그래서 파일별 고립 DPS만 보는 화력 추정은 실제보다 항상 보수적이다. 버그가 아니라 관통 규칙의 귀결이다.

이 차이는 실측에서 극단적으로 드러난다(§9.5): 8파일 동시 배치의 룩 1개/파일은 w16~w19 누수 0인데, **완전히 고립된 룩 1기는 w19에서 한 마리도 못 잡는다**(24초 동안 40~45 < 체력 55).

### 4.7 퀸 — 900G / 공격력 0 / 공격 없음

**버프 범위: 자기 칸 + 8방향 직선 끝까지** (22~28칸, 중앙 28). 경로에 다른 기물이 있어도 **차단되지 않는다.**

`attackTargets`가 빈 배열을 돌려주므로 **유일한 능력치는 8방향 라인 버프**다.

- 라인 위 아군 1기당 `queenBuffCount += 2^(퀸의 강화단계−1)`로 누적된다.
- **퀸이 겹치면 그만큼 더 쌓인다.**
- **퀸 자신은 계산에서 명시적으로 제외된다** (`if (p === q) continue`). 실제로 버프가 닿는 대상 칸은 중앙 기준 최대 27칸이다.
- 슬롯에 있는 기물의 퀸 버프는 항상 0이다.
- **골드에는 적용되지 않는다** (사용자 결정). 그 규칙의 유일한 근거지는 `pieceGold` 함수 하나다.

> ⚠️ **이 식 전체가 `buff.ts:22` 한 줄에만 산다.** `CONFIG`에는 퀸 버프를 조정할 값이 없다 — 기준값 +1도 `tierMultiplier(1)`에서 우연히 나오는 값이지 설정 항목이 아니다. §4.5의 "골드 미적용의 유일한 근거지는 `pieceGold`"와 같은 성격이며, 밸런스를 바꾸려면 `config.ts`가 아니라 `buff.ts`를 열어야 한다.

> ⚠️ **툴팁과 시작 화면은 이 값을 파생시키지 않는다.** 언제나 "+100%" / "×2"라고 말하므로 T2 이상 퀸에서 **표시가 실제보다 낮게 나온다** — 배치 판단을 직접 왜곡하는 현존 버그다(§12.1-B).

> **왜 퀸 자신을 명시적으로 제외하는가** — "포함되지만 실효가 없는" 게 아니라 명시적 제외다. 퀸이 합성이나 향후 변경으로 공격력을 갖게 돼도 규칙이 흔들리지 않는다.

**재계산은 이벤트 트리거다.** 매 프레임 재계산하지 않고, 배치·이동(맞교환 포함)·회수·판매·합성 커밋 직후에만 `recalcQueenBuffs`를 돈다. 슬롯 내 재정렬은 트리거가 아니다(슬롯 기물은 늘 0이므로 불필요).

> **의도된 최적화이지만 책임이 따른다** — 기물 배치를 바꾸는 **모든 경로가 재계산을 직접 호출할 책임**을 진다. 앞으로 코어가 기물 위치를 스스로 바꾸는 기능(자동 배치·소환 등)을 추가하면 그 경로에서 `recalcQueenBuffs`를 직접 불러야 한다. **부르지 않아도 아무 에러 없이 옛 배율로 계속 싸운다.**

**퀸도 T6까지 열려 있다** — 한 퀸이 주는 최대 버프는 +32(배율 ×33)이고, T6 퀸 두 기의 라인이 겹치면 +64(배율 ×65)다. 다만 **누적 비용이 상한을 실질적으로 막는다**: T6 퀸 하나에 기본 퀸 32기 = 28,800G가 필요한데 한 판 총 골드가 24,702G다. 현실적인 상한은 T4(7,200G, +8 = 배율 ×9)이고, 두 기가 겹치면 ×17이다. (이 상한은 원래 3이었다 — 변경 이력과 근거는 §12.8.)

### 4.8 조작 가능 조건

기물 조작(배치·이동·회수·재정렬·합성·구매·판매)은 **`paused`가 아니고 `phase`가 `prepare` 또는 `wave`일 때만** 가능하다. **웨이브 진행 중에도 구매·배치·재배치가 자유롭다.** `victory`/`defeat` 이후에는 전부 거부된다. 게이트의 구현 위치와 그 비대칭은 §7.6에 정리했다.

## 5. 합성 시스템 (v1.8)

### 5.1 한 줄 요약

**같은 종류 · 같은 티어**의 기물을 **드래그로** 겹치면 티어가 **정확히 한 단계** 오른다. (흰+흰=녹, 녹+녹=파, 파+파=보, 보+보=노, 노+노=빨)

### 5.2 티어와 배수

**능력치 배수 = 2^(tier − 1)** — 배열이 아니라 식이다.

| 티어 | T1 | T2 | T3 | T4 | T5 | T6 |
|---|---|---|---|---|---|---|
| 배수 | ×1 | ×2 | ×4 | ×8 | ×16 | ×32 |
| 링 색 | #FFFFFF (그리지 않음) | #3BA55C 녹 | #3B82D6 파 | #8B5CF6 보 | #E0B400 노 | #DC3B3B 빨 |

**상한** — 5종 모두 **6**(테두리 색 6단계와 같은 수).

> **왜 식으로 두는가** — 상한을 바꿔도 표를 함께 고칠 필요가 없다. `enemyHp`/`enemyCount`와 같은 "CONFIG에서 유도하는 함수" 선례를 따른다.

> **퀸은 성질이 다르다는 것을 알고 연 것이다** — 퀸의 버프는 **다른 모든 기물의 공격력에 곱해지는 유일한 값**이라, 퀸의 티어 상한은 그대로 게임 전체 화력의 지수가 된다. 상한을 6으로 연 것은 그 사실을 알고 내린 결정이고(§12.8), 밸런스가 무너지면 `queen`만 3으로 되돌리는 것이 가장 국소적인 처방이다.

### 5.3 능력치 연동 — 네 곳 전부 티어를 곱한다

| 대상 | 식 | 티어 곱셈의 근거 |
|---|---|---|
| **공격력** | 기본 × 2^(t−1) × (1 + 퀸버프) | 퀸 라인 위 T1 룩 2기(각 10, 합 20)와 T2 룩 1기(5×2×2=20)가 같아야 "능력치 합"이 성립한다. **덧셈으로 넣으면 버프받은 기물을 합칠 때만 값이 어긋난다.** |
| **비숍 골드** | 10 × 2^(t−1) | **함정 방지.** 수입은 발사 횟수에 비례하는데 합성은 발사체 수를 절반으로 줄인다. 곱하지 않으면 같은 3,200G에서 20웨이브 총 수입이 T1 16기 **+19,940G → T2 8기 +9,750G로 51% 증발**하는데, 판매가와 툴팁은 가치가 보존된 것처럼 표시해 **손실이 어디에도 드러나지 않는다.** |
| **퀸 버프** | += 2^(t−1) | 안 하면 퀸 2기를 합쳤을 때 배율이 ×3 → ×2로 떨어져 **1,800G를 쓴 플레이어가 벌을 받는다.** T2 퀸 하나 = T1 퀸 둘 = +2, 비용도 1,800G로 같다. 툴팁은 이 값을 파생시킨다(§12.8); 시작 화면 산문만 하드코딩이다. |
| **판매가** | 원가 × 2^(t−1) × 0.5 | 안 곱하면 합성이 **보이지 않는 골드 소각**이 된다(룩 2기 1,000G를 합쳐 팔면 250G만 회수). 게다가 `sellPrice`가 `type`만 받던 탓에 그 손실이 어떤 테스트에도 걸리지 않았다. ⚠️ 판매 **프리뷰**는 여전히 티어를 무시한다(§12.1-A). |

### 5.4 합성은 증폭이 아니라 **압축**이다

배수와 누적 비용이 **둘 다 2의 거듭제곱**이라 골드당 화력이 티어와 무관하게 일정하다 — **골드 축에서 정확히 중립이다.**

| 통제 실측 | 결과 |
|---|---|
| 8,000G 룩 16×T1 vs 8×T2 | w16~w19 **누수 0으로 완전 동률** |
| 20웨이브 최소 승리 비용 | **18,800G로 동일** (합성 유무 무관) |
| 달라지는 것 | **방어선이 차지하는 칸 수뿐 — 28칸 → 8칸** |

**플레이 상의 의미는 오직 '문턱'에서 나온다.**

룩 2기가 적 한 마리에게 넣는 총딜은 45(자기 파일 8발 + 상대 랭크 1발)다. w16의 43은 넘지만 **w17의 47은 못 넘고, 못 넘으면 그 피해는 부분 크레딧 없이 전량 폐기된다**(적이 살아서 통과).

> 같은 1,000G로 w17에서 — **룩 2×T1은 처치 0, 룩 1×T2는 처치 6.**

**결론: 화력이 문턱을 넉넉히 넘으면 흩어놓는 쪽이, 문턱에 걸리면 합치는 쪽이 옳다.**

> **이 중립성은 퀸에는 성립하지 않는다.** 퀸의 버프는 다른 모든 기물의 공격력에 곱해지므로 퀸의 티어는 골드당 화력이 아니라 **보드 전체 화력의 지수**다. 상한을 6까지 연 지금(§12.8) T6 퀸 두 기가 교차하는 칸은 배율 ×65이고, 그 칸의 T6 룩은 공격력 10,400 — w20 보스 체력의 5.9배를 한 발에 낸다. 이 조합은 비용(퀸만 57,600G)이 총 골드를 훨씬 넘어 실전에서는 도달하지 못하지만, **퀸의 티어만은 골드 중립이 아니라는 사실 자체는 남는다.**

### 5.5 착지 판정 — `resolveLanding` 하나가 전담한다

실제 규칙(`moveOnBoard`/`placeFromSlot`)과 미리보기(`buildHighlights`)가 **모두 이 함수만 호출한다.** 그래서 미리보기가 **착지 규칙에 관한 한** 실제로는 거부될 동작을 약속할 수 없다(그 계약의 정확한 범위는 §7.3).

판정 결과는 5값 판별 유니온 `Landing`이다.

| kind | 의미 | 동봉 |
|---|---|---|
| `place` | 빈 칸 배치 | — |
| `merge` | 합성 | `occupant`, `resultTier` |
| `swap` | 맞교환 | `occupant` |
| `self` | 자기 칸 (실제 조작 경로에서는 도달 불가 — §5.7) | `occupant` |
| `reject` | 거부 | `reason` |

**거부 사유는 6종이다.**

| 사유 | 조건 |
|---|---|
| `outOfBounds` | 보드 밖 또는 8랭크 |
| `knightCooldown` | **보드발** 나이트가 쿨다운 중이거나, 합성 대상 **점유자 나이트**가 쿨다운 중 |
| `knightPattern` | **보드발** 나이트의 목적지가 L자 행마가 아님 |
| `typeMismatch` | **트레이발이 점유 칸에 착지** — 합성 분기를 타지 못한 모든 경우 |
| `tierMismatch` | 트레이발 + `allowMerge` + 같은 종류 + **다른 티어** |
| `tierOverflow` | 같은 종류·같은 티어지만 결과가 상한 초과 |

> ⚠️ **`typeMismatch`는 이름과 달리 '종류 불일치'가 아니다.** `pieces.ts:105-109`는 합성 분기를 타지 못한 **모든** 트레이발 점유-칸 착지에 이 사유를 붙인다 — 종류가 같아도 `allowMerge=false`(클릭-투-무브)면 티어가 같든 다르든 `typeMismatch`다. 실제 의미는 **"트레이발은 점유 칸에 착지할 수 없다"**이며, 이름은 합성 도입 이전의 잔재다.

> **왜 boolean에서 유니온으로 승격했는가** — 합성이 들어오면서 같은 칸이 **출발지와 제스처에 따라** 배치·합성·맞교환·거부 넷 중 하나가 되어 2값으로는 표현할 수 없게 됐다. `canLandAt`은 이제 `resolveLanding(..., false).kind !== 'reject'`의 한 줄 파생이며, 합성 도입 이전과 의미가 정확히 같다.

### 5.6 게이트 순서 — 순서가 곧 규칙이다

```
(1) 경계 (8랭크 / 보드 밖)
(2) 보드발 나이트 쿨다운
(3) 보드발 나이트 L자
(4) 점유자 유무          → 없으면 place
(5) 자기 자신            → self
(6) 합성 분기            → merge / tierMismatch / knightCooldown / tierOverflow
(7) 트레이발 점유 거부    → typeMismatch
(8) 맞교환               → swap
```

> **합성 분기는 반드시 경계·나이트 게이트 *뒤*에 온다.** 앞으로 당기면 8랭크 금지와 나이트 L자/쿨다운 제약을 **합성 경로가 통째로 우회한다.** 이 순서 때문에 **보드 위 나이트끼리의 합성은 L자 거리에서만 성립한다**(§4.4).

### 5.7 판정표

아래 표의 '보드' 행 중 나이트는 **(2)(3) 게이트를 이미 통과한 경우**만 해당한다 — 쿨다운이 남았거나 목적지가 L자가 아니면 목적지 상태와 무관하게 `knightCooldown` / `knightPattern` 거부다.

| 출발 | 목적지 상태 | 드래그 (allowMerge=true) | 클릭-투-무브 (false) |
|---|---|---|---|
| 보드 | 빈 칸 | `place` | `place` |
| 트레이 | 빈 칸 | `place` | `place` |
| 보드 | **같은 종류 · 같은 티어** | **`merge`** (tier+1) | `swap` |
| 트레이 | **같은 종류 · 같은 티어** | **`merge`** | `reject` typeMismatch |
| 보드 | 같은 종류 · **다른 티어** | `swap` | `swap` |
| 트레이 | 같은 종류 · **다른 티어** | `reject` tierMismatch | `reject` typeMismatch |
| 보드 | 다른 종류 | `swap` | `swap` |
| 트레이 | 다른 종류 | `reject` typeMismatch | `reject` typeMismatch |
| 보드 | 같은 종류·같은 티어, **상한 초과** | `reject` tierOverflow | `swap` |
| 트레이 | 같은 종류·같은 티어, **상한 초과** | `reject` tierOverflow | `reject` typeMismatch |
| 아무 | 보드 밖 / 8랭크 | `reject` outOfBounds (`occupant: null`) | 동일 |
| 보드 (나이트) | 쿨다운 중 | `reject` knightCooldown | 동일 |
| 보드 (나이트) | L자 아님 (**빈 칸·합성 대상 포함**) | `reject` knightPattern | 동일 |
| 보드 (합성 대상이 나이트) | 점유자 쿨다운 중 | `reject` knightCooldown | (합성 분기 아님 → `swap`) |

**나이트 특례 — 쿨다운은 출발지에 따라 검사 범위가 다르다.**

| 출발 | 검사되는 쿨다운 | L자 게이트 |
|---|---|---|
| **보드발** | **양쪽** (자신 = 게이트 (2), 점유자 = 합성 분기) | 적용 |
| **트레이발** | **점유자 쪽만** | 미적용 |

`pieces.ts:78-79`의 자기 쿨다운·L자 검사가 `fromBoard` 조건 안에 있기 때문이다. 그래서 **쿨다운이 남은 트레이 나이트를 쿨다운 0인 보드 나이트 위로 드래그하면 합성이 그대로 성립한다.** 트레이 나이트는 착지 가능한 아무 칸의 같은 티어 나이트 위로 갈 수 있다.

> **왜 점유자 쪽 쿨다운은 항상 검사하는가** — 검사하지 않으면 합성은 성사되는데 직후 `tryKnightBlast`가 `cooldown > 0`에 걸려 **폭발을 조용히 삼킨다.** 미리보기가 그린 3×3이 실제로는 0회가 되는, 이 파일이 막으려는 바로 그 상황이다.

**`self`는 실제 조작 경로에 도달하지 않는다.** `moveOnBoard`는 `resolveLanding`을 부르기 **전에** `pieces.ts:205`의 `sameSquare(...) → return false`로 빠지고, 그 `false`가 `drag.ts:225→258`의 `playDropCue`에서 거부로 처리돼 **`uiInvalid` 거부음이 난다**(칸 이동이 6px 이상이면 클릭이 아니라 드래그로 판정되므로 같은 칸 안에서도 재현된다). 클릭-투-무브도 같은 기물을 다시 클릭하면 선택 해제로 빠져 `resolveLanding`에 도달하지 않는다. `moveOnBoard`의 `landing.kind === 'self'` 분기(`pieces.ts:209`)와 `Landing`의 `self` 케이스는 **도달 불가 방어 코드**이며, "조용한 no-op"이 아니라 실제로는 거부 피드백이 난다.

### 5.8 합성 커밋

합성이 실제로 일어나는 유일한 함수는 `commitMerge` 하나다(맞교환이 `moveOnBoard` 한 곳인 것과 같다).

| 규칙 | 내용 | 근거 |
|---|---|---|
| **생존자** | **이미 그 칸에 있던 점유자.** 드래그한 쪽이 흡수돼 사라진다 | 사라지는 id가 항상 `dragging`에 들어 있는 id가 되어, 드래그 종료 시 어차피 null로 비우는 값이므로 새 dangling 위험이 없다 |
| **결과 티어** | 생존자.tier + 1 | 같은 티어끼리만 합쳐지므로 결과는 언제나 정확히 한 단계 위 |
| **쿨다운** | **생존자 것을 그대로 둔다** | **안티파밍.** '둘 중 작은 값' 승계로 하면 구매→합성이 **쿨다운 초기화 버튼**이 되어, 쿨다운을 기물 ID에 묶어 둔 규칙이 통째로 무너진다 |
| **배열 제거** | 흡수된 기물을 `state.pieces`에서 `splice`로 제거 | `pieceAt`/`pieceUnder`/`updateSlots`/`tooltip`이 전부 **첫 일치만** 집으므로, 같은 칸에 두 기물이 남으면 아래 깔린 쪽이 **영원히 조작 불가능**해진다 |
| **버프 재계산** | 항상 `recalcQueenBuffs` 호출 | 흡수된 쪽이 퀸이 아니어도 **퀸 라인 위에 있었을 수 있다** |
| **이벤트** | `merged` 정확히 1건 (square = 생존자 칸, tier = 합성 **후**) | — |
| **나이트 폭발** | 생존자 기준 정확히 1회, **갱신된 티어**의 데미지로 | "플레이어가 직접 움직인 기물만 폭발한다"는 맞교환 규칙과 같은 근거 — 다만 합성에서는 움직인 쪽이 사라지므로 그 화력이 생존자에게 넘어간다 |

**트레이발 합성은 슬롯을 하나 비워 `canBuy`를 다시 연다.** 보드가 꽉 찬 후반에도 구매 루프가 계속 돌게 하는 **의도된 동작**이다(`pieces.ts:174-175`).

> **다만 슬롯을 비우는 유일한 경로는 아니다.** ① `sellPiece`가 트레이 기물을 `state.pieces`에서 splice하면 그 슬롯이 그대로 빈다(`economy.ts:48-53`). ② **보드발** 합성으로 보드 칸이 하나 비면 `placeFromSlot`이 다시 열려 트레이가 비워진다. 합성의 값어치는 "유일한 출구"라서가 아니라 **손실 없이 슬롯을 비우는 유일한 방법**(판매는 50%를 태운다)이라는 데 있다.

### 5.9 설계 결정 모음

> **왜 드래그 앤 드롭 전용인가** — 합성은 비가역인데 클릭-투-무브에는 "기물을 클릭해 선택을 옮기는" 조작과 구분할 방법이 없다. **확인창을 띄우는 대신 제스처 자체를 분리했다.** 덤으로 같은 종류끼리 자리를 바꾸는 조작이 합성 도입 후에도 그대로 남는다.

> **왜 같은 티어끼리만인가** — 이 제약이 있어야 tier가 "흡수한 개수"가 아니라 **레벨**이 되고, 배수가 단계마다 정확히 2배로 떨어진다. 동시에 **강화된 기물이 약한 기물에 겹쳐져 조용히 잡아먹히는 사고를 규칙 차원에서 막는다.**

> **왜 상한 초과를 맞교환으로 폴백하지 않고 완전 거부하는가** — 같은 종류 위로 드래그하는 의도는 **언제나 합성**인데, 대신 자리를 바꿔 주면 공들여 짜 둔 배치가 **예고 없이** 흐트러진다(합성 미리보기도 뜨지 않는 상태다). 거부하면 원위치 복귀 + `uiInvalid`로 알린다. 자리를 바꾸고 싶으면 클릭-투-무브를 쓴다.

> **왜 트레이발은 점유 칸에 못 가는가** — 맞교환은 **밀려날 기물이 되돌아갈 출발 칸**을 필요로 하는데 트레이발에는 그 칸이 없다. 합성만 예외인 건 한쪽이 사라져 되돌아갈 자리가 애초에 필요 없기 때문이다.

### 5.10 미리보기

- 드래그 중 합성 대상 칸을 **마젠타** `rgba(214,51,132,0.55)`로 칠하고, 그 위에 **결과 티어 색의 점선 링**(반지름 43px, dash [6,5]) + **`T{n}` 라벨**을 그린다.
- **합성 미리보기가 뜨는 프레임에는 사거리/퀸 라인 미리보기를 그리지 않고 즉시 반환한다.**
- 미리보기의 `allowMerge`는 `it.dragging`의 유무에서 유도한다 — `drag.ts`와 `highlights.ts`가 **같은 사실에서 같은 값**을 만드므로 갈라질 수 없다.

> **왜 사거리를 함께 그리지 않는가** — 합성은 이동이 아니라 **흡수**다. 사거리를 그리면 "이 칸으로 옮겨간다"는 잘못된 인상을 준다.

> **왜 마젠타인가** — 기존 팔레트(주황 사거리·초록 이동·파랑 퀸라인·노랑 선택) 어느 것과도 겹치지 않고, 그 위에 겹쳐 그리는 티어 6색과도 구분된다.

> **왜 라벨이 `T3` 형식인가** — `renderer.test.ts`가 '×'로 시작하는 `fillText` 전량을 퀸 버프 배지로 못박고 있어 '×' 접두사를 쓸 수 없다.

**합성 성사 자체는 무음이다**(`merged` → null). 화면 표시는 결과 티어 색으로 퍼지는 링 이펙트(`mergeBurst`, 0.45초)가 담당한다. 나이트 합성만은 직후 `knightBlast`가 따라와 폭발음이 난다.

## 6. 경제

### 6.1 골드 획득 경로 — 정확히 넷

`state.gold`를 늘리는 코드는 이 넷과 판매 환급이 전부다.

| 경로 | 값 | 조건 |
|---|---|---|
| **시작 골드** | 300G | — |
| **적 처치** | 그 적의 **maxHp**와 정확히 같음 (보스 포함) | **처치했을 때만.** 누수한 적은 0G |
| **웨이브 클리어 보너스** | **300G 정액** | 웨이브 번호 무관. **방어 성공과 무관** |
| **비숍 공격당 골드** | 10G × 2^(tier−1) | 발사 1회당 정액 |

> **왜 처치 골드가 maxHp인가** — 오버킬·분산 딜과 무관하게 **적 1마리의 경제적 가치를 고정**하기 위해서다. 그 결과 **처치 골드 총합**이 배치와 무관하게 config만으로 완전히 유도 가능해졌고, 밸런스 테스트가 하드코딩 없이 그 값을 계산할 수 있다.

> ⚠️ **"한 판에 벌 수 있는 총 골드"는 config만으로 유도되지 않는다.** 위 넷 중 **비숍 골드는 발사 횟수에 비례**하므로 배치와 적 체류 시간에 좌우된다 — 비숍 1기당 한 판 112~185발 = **1,120~1,850G**의 폭이 있다(`config.ts:34-38` 실측). config만으로 닫히는 것은 처치 골드·클리어 보너스·시작 골드 셋뿐이다. §6.4·§9.1의 모든 합계는 **비숍 0기 기준**이라는 뜻이다.

> **클리어 보너스는 방어 성공의 대가가 아니라 웨이브 종료의 대가다.** 클리어 판정이 "보드에 적 0"만 보므로 **적을 전부 누수시켜도 300G는 그대로 들어온다.** 체력만 버틸 수 있다면 누수 방치는 클리어 보너스 손실 없이 처치 골드만 포기하는 선택지가 된다.

### 6.2 구매

**조건 네 가지 동시 충족** — ① 일시정지 아님 ② `phase`가 `prepare` 또는 `wave` ③ 골드 ≥ 원가 ④ **빈 슬롯 존재**

- 구매한 기물은 **언제나 가장 낮은 번호의 빈 트레이 슬롯**에 들어간다. **보드에 직접 놓이는 경로는 없다.**
- 트레이 용량 = 4×4 = **16칸**.
- 구매 직후 기물은 **tier 1 · 쿨다운 0**.

> **후반의 실제 병목은 골드가 아니라 슬롯이다.** 보드에 자리가 남아도 트레이 16칸이 꽉 차면 `canBuy`가 false가 되어 구매 자체가 막힌다. 합성의 압축 가치가 여기서 나온다. 같은 이유로 **보드 → 트레이 회수도 트레이가 꽉 차면 거부된다**(§7.1).

상점 버튼은 매 프레임 `canBuy` 결과로 `disabled`가 갱신되고, 그와 **별개로** `wireShop`이 `buyPiece` 반환값으로 성공을 재판정해 `uiBuy`를 울린다 — 버튼 비활성화 사실에 기대지 않는다.

### 6.3 판매

**판매가 = 원가 × 2^(tier−1) × 0.5**

| 기물 | T1 | T2 | T3 | T6 |
|---|---:|---:|---:|---:|
| 폰 | 50G | 100G | 200G | 1,600G |
| 나이트 | 150G | 300G | 600G | 4,800G |
| 비숍 | 100G | 200G | 400G | 3,200G |
| 룩 | 250G | 500G | 1,000G | 8,000G |
| 퀸 | 450G | 900G | 1,800G | 14,400G |

- **보드·트레이 어디의 기물이든 확인창 없이 즉시 성사된다.** 일시정지/승리/패배 중에만 거부된다(§7.6).
- 판매 직후 반드시 `recalcQueenBuffs`를 돈다 — 판 것이 퀸이든 버프 대상이든 라인이 달라지기 때문이다.
- **합성 후 판매액 = 합성 전 두 기물 판매액의 합**이 정확히 성립한다.
- 구매 후 즉시 판매하면 원가의 50%가 소각된다.
- ⚠️ **판매 프리뷰는 이 표를 따르지 않는다** — 언제나 T1 가격을 띄운다(§12.1-A).

### 6.4 한 판 총 골드

| 항목 | 값 |
|---|---:|
| 시작 골드 | 300G |
| 처치 골드 총합 | **18,402G** (일반 14,472 + 보스 3,930) |
| 클리어 보너스 총합 | 300G × 20 = **6,000G** |
| **소계 — 비숍 0기 · 무누수 · 전량 처치** | **24,702G** |
| 비숍 수입 | 위 소계에 **포함되지 않음.** 비숍 1기당 **1,120~1,850G**, 대수만큼 계속 커진다 |

**전후반 분포 — 처치 골드의 83%가 후반에 몰린다.**

| 구간 | 처치 골드 | 비중 |
|---|---:|---:|
| w1~w10 | 3,126G | **17.0%** |
| w11~w20 | 15,276G | **83.0%** |

> 이 비대칭은 `hpPerWaveLate` 하나에서 나온다. 처치 보상이 maxHp라서 후반 HP 증가폭 4가 골드 곡선에도 그대로 실린다. **초반 골드 부족이 심하고 후반에는 남아돈다.**

**20웨이브 최소 승리 비용은 18,800G**(룩16 + 퀸12, 합성 유무 무관)다. 비숍 없는 총 골드 24,702G 대비 여유 5,902G(24%)로 보이지만, **골드의 83%가 후반에 들어오므로 초반 문턱이 실질 제약이다.** 단순 차감으로 읽으면 안 되고, 비숍을 사면 총액 자체가 커진다.

> **통계 주의** — `state.stats.totalGoldEarned`에는 **시작 골드 300G가 포함되지 않고, 판매 환급도 집계되지 않는다.** 집계되는 것은 처치(`combat.ts:49`) + 클리어 보너스(`wave.ts:42`) + 비숍 수입(`combat.ts:85`) 셋이다. **비숍이 0기일 때의 최댓값이 24,402G**(= 18,402 + 6,000)이고, 비숍이 한 기라도 있으면 그만큼 초과한다 — **상한이 아니라 하한에 가깝다.**

## 7. 조작

### 7.1 동작표

| 출발 → 목적지 | 결과 |
|---|---|
| 트레이 → 보드 빈 칸 | **배치** |
| 트레이 → 보드 점유 칸 (같은 종류·같은 티어·상한 미달, 드래그) | **합성** |
| 트레이 → 보드 점유 칸 (그 외) | **거부** (원위치 복귀) |
| 트레이 → 트레이 | **재정렬** (점유 시 맞교환) |
| 보드 → 보드 빈 칸 | **이동** — 단 나이트는 L자 + 쿨다운 0일 때만, 아니면 거부 |
| 보드 → 보드 점유 칸 (같은 종류·같은 티어·상한 미달, 드래그) | **합성** |
| 보드 → 보드 점유 칸 (같은 종류·같은 티어·**상한 초과**, 드래그) | **거부** `tierOverflow` — 맞교환으로 폴백하지 않는다 |
| 보드 → 보드 점유 칸 (그 외) | **맞교환** |
| 보드 → 트레이 (빈 슬롯 있음) | **회수** (선호 슬롯이 비었으면 그 자리, 아니면 첫 빈 슬롯) |
| 보드 → 트레이 (**16칸 전부 점유**) | **거부** — `recallToSlot`이 `freeSlotIndex === null`에서 false를 돌려준다 (`pieces.ts:226-241`) |
| 어디서든 → 판매 슬롯 | **판매** |
| 그 외 | 원위치 복귀 |

> **같은 조작이 제스처에 따라 정반대 결과가 되는 유일한 지점**은 상한 초과 합성이다 — 드래그는 거부, 클릭-투-무브는 맞교환. 5종 모두 T6 두 기가 여기 해당한다.

**드롭 대상 판정 우선순위: 판매 슬롯 > 트레이 슬롯 > 보드 > null.** 영역이 겹치면 **항상 판매가 이긴다.**

**맞교환의 세부 규칙**

- 목적지가 점유돼 있으면 실패가 아니라 **두 기물의 자리 맞교환**이다.
- 어느 쪽의 **쿨다운도 초기화하지 않는다.**
- **밀려난 기물은 나이트여도 폭발하지 않는다** — 스스로 움직인 것이 아니기 때문이다.
- 버프 재계산은 두 `square` 갱신이 **모두 끝난 뒤** 정확히 한 번 돈다.
- **보드 → 이미 점유된 트레이 칸은 맞교환이 아니다** — 가장 낮은 빈 슬롯으로 회수되고 점유자는 그대로 있다. 트레이 내 재정렬(`reorderSlots`)만 맞교환한다.

### 7.2 제스처

| 제스처 | 규칙 |
|---|---|
| **클릭 판정** | 6px 미만 이동 후 놓으면 클릭 |
| **클릭-투-무브** | 첫 클릭 = 선택, 둘째 클릭 = 실행. 같은 기물 재클릭 = 선택 해제 |
| **Esc** | 선택과 진행 중인 드래그를 함께 취소 |
| **드래그 종료 후** | 이전 클릭 선택을 **반드시 비운다** |

> **왜 드래그 후 선택을 비우는가** — 남겨 두면 이후의 **판매 슬롯 클릭이 겨냥한 적 없는 기물을 팔아 버린다.**

**취소·이탈 경로는 셋이다**(`drag.ts:265-276`).

| 이벤트 | 동작 |
|---|---|
| `Escape` | 선택 해제 + 진행 중 드래그 취소(고스트·판매 프리뷰 정리) |
| `pointercancel` (터치 취소 등) | **드롭을 시도하지 않고** `downAt`·`dragging`을 비우고 고스트·판매 프리뷰만 정리 |
| `pointerleave` (포인터가 창 밖으로) | `hoverSquare`만 null로 — 드래그 자체는 유지 |

**나이트 집기 거부** — 보드 위 나이트는 쿨다운이 남아 있으면 **집는 것 자체가 거부**되고 커서 옆에 "이동 쿨다운 N.Ns" 라벨이 0.8초 뜬다. 이때 `downAt`을 null로 비워 그 눌림이 클릭-투-무브 선택으로 새어나가지 않게 한다. **트레이의 나이트는 쿨다운이 남아 있어도 언제나 집을 수 있다.**

### 7.3 미리보기 = 실제 규칙 계약 (그 정확한 범위)

**이 코드베이스의 핵심 불변식이다 — 다만 계약의 범위가 정해져 있다.**

```
실제 규칙 (moveOnBoard / placeFromSlot)  ┐
                                          ├──> resolveLanding  (단 하나)
미리보기 (render/highlights.ts)           ┘
```

**계약이 보장하는 것** — `resolveLanding`이 소유한 착지 규칙(8랭크 금지·나이트 L자/쿨다운·티어 상한·트레이발 점유 금지)에 관해서는, 미리보기가 실제로는 거부될 이동·배치·합성을 약속하는 일이 **구조적으로 불가능**하다. 미리보기가 이 게이트들을 **따로 재구현하지 않는다.**

**계약이 보장하지 않는 것** — 커밋 함수는 `resolveLanding` **위에 `interactable()` 게이트를 하나 더** 통과해야 한다(`pieces.ts:146-148`, 호출부 170·204·228·247). 그런데 `render/highlights.ts`는 `state.phase`도 `state.paused`도 **한 번도 읽지 않는다**(`render/` 전체에 두 필드 참조 0건).

> ⚠️ **그래서 `victory`/`defeat`에서 미리보기가 거짓말을 한다.** 이 페이즈에서는 `paused`가 false라 `DragController`가 그대로 동작하고(핸들러가 `document` 레벨 좌표 판정이라 결과 오버레이도 막지 못한다), 초록·주황·마젠타 미리보기가 계속 뜬다. 그러나 `moveOnBoard`/`placeFromSlot`/`recallToSlot`은 전부 false를 돌려주므로 실제로는 **`uiInvalid`로 끝난다.** §7.4의 판매 프리뷰도 같은 구멍이다.

부속 규칙들:

- 나이트 초록 이동칸과 hover 폭발 미리보기는 **동일한 `legalMoves`** 하나만 쓴다. 쿨다운 중에는 `legalMoves`가 통째로 비어 초록도 폭발 미리보기도 뜨지 않는다.
- 착지 불가한 칸에 hover하면 **미리보기 전체를 접되 선택 표식(노랑)은 유지한다** — "이동할 수 없다"와 "선택되지 않았다"는 다른 상태다.
- 선택 표식은 **항상 각 분기의 마지막에 push한다** — 렌더가 배열 순서대로 알파 블렌드하므로 사거리·퀸라인보다 먼저 넣으면 그 밑에 묻힌다.

### 7.4 판매 프리뷰

판매 슬롯 hover 시 `.armed` 배경과 "+NG" 환급 프리뷰가 뜬다. **드래그 중뿐 아니라 클릭으로 선택된 상태에서도 동작한다.**

> **왜 두 제스처 모두에 필요한가** — 판매에는 확인창이 없으므로 **프리뷰가 유일한 안전장치**다.

> ⚠️ **현재 이 프리뷰에 버그가 둘 있다.** ① 강화 단계를 무시한다(§12.1-A). ② `drag.ts:198-206`이 페이즈를 보지 않아, `sellPiece`가 거부하는 `victory`/`defeat`에서도 "+NG"를 띄운다.

### 7.5 사운드

| 상황 | 큐 |
|---|---|
| 거부 (원위치 복귀) | `uiInvalid` — 조용히 되돌아가는 그 순간의 **유일한** 청각 피드백 |
| 판매 | `uiSell` |
| 트레이 내 재정렬 | **의도적 무음** |
| 그 외 성공 (배치/이동/회수) | `uiPlace` |
| 집기 / 선택 시작 | **무음** (v1.4에서 큐 자체를 제거) |

### 7.6 페이즈·일시정지 게이트 — 구현이 두 벌이다

| 대상 | 게이트 | 위치 |
|---|---|---|
| 배치 · 이동 · 회수 · 재정렬 · 합성 | `interactable(state)` = `!paused && (phase === 'prepare' \|\| phase === 'wave')` | `pieces.ts:146-148` |
| 구매 | `canBuy` 안에 같은 조건을 **다시 적는다** | `economy.ts:19-24` |
| 판매 | `paused \|\| phase === 'victory' \|\| phase === 'defeat'` → 거부 | `economy.ts:49` |

`Phase`가 정확히 4값이므로 **세 조건은 현재 논리적으로 동치**다. 그러나 **같은 규칙이 세 곳에 따로 적혀 있다** — 페이즈를 하나라도 추가하면(예: `paused`를 페이즈로 승격, 결과 화면 전용 페이즈 도입) 세 곳이 조용히 갈라진다. §10.5의 "불변식은 함수 하나에 가둔다" 원칙이 이 규칙에만 적용되어 있지 않다.

`DragController` 쪽 게이팅은 또 다르다. `onDown`/`onUp`만 `paused`에서 조기 반환하고, **`onMove`는 계속 돈다** — 일시정지 중에도 `hoverSquare` 갱신과 판매 프리뷰 표시가 살아 있다.

### 7.7 성능

`getBoundingClientRect`는 **드래그 시작 시점에 한 번 읽고** resize/scroll 전까지 캐시를 재사용한다.

> **왜 캐시하는가** — 매 `pointermove`(~100Hz)마다 부르면 강제 레이아웃이 발생한다. **이 게임에서는 드래그 응답성이 곧 보스전 난이도다.**

## 8. 표현

### 8.1 화면 구성

**페이지를 열면 보드가 아니라 시작 화면이 뜬다.** BATTLE을 누를 때까지 **캔버스도, 프레임 루프도, AudioContext도 만들어지지 않는다.**

> **왜 시작 화면을 도입했는가** — 규칙을 모르는 사람이 기물 설명부터 읽고 들어갈 수 있게 하기 위해서다. 부수 효과로 시작 화면 동안에는 프레임 루프도 AudioContext도 아예 존재하지 않는다.

**시작 화면** (최대 880px 한 단) — 제목 / 기물 탭 5개 + 패널 / BATTLE 버튼 + 힌트 / 저작자 표시줄

각 기물 패널: 아이콘·이름·역할·가격/판매가 헤드 + **5×5 사거리 그림** + (공격력/공격 주기/골드/합성/속성) dl + 산문 설명.

> **왜 사거리 그림이 d4 기준 반경 2인가** — 5×5 창이 보드 밖으로 잘리면 "여기서 사거리가 끝난다"는 잘못된 인상을 준다. 한가운데를 골라 잘리지 않게 했다. rank를 위로 갈수록 크게 그리는 것도 **폰이 적 쪽(위)을 친다는 게 보이게** 하기 위해서다.

> **왜 `#title-panels`에 `min-height`를 깔았는가** — 기물마다 설명 길이가 달라 탭을 옮길 때마다 상자 높이가 튀고 BATTLE 버튼까지 따라 움직인다. 가장 긴 패널(나이트)에 맞춰 바닥을 깔았다.

**게임 화면 4단** — 상단 HUD / 3단 본문(좌 210px 슬롯+상점 · 중앙 640×640 캔버스 · 우 210px 판매 슬롯+웨이브 시작) / 저작자 표시줄 / 배너 레이어

**HUD 8항목** — 체력 ♥ / 골드 💰 / 웨이브 N/20 / 남은 적 / 타이머 ⏱ + 보스 아이콘 / 일시정지 / 배속 / 음소거

- 타이머는 `prepare`에서만 0.1초 단위로 표시하고 그 외에는 `—`.
- **'남은 적'은 페이즈마다 의미가 다르다**: `wave` 중에는 (총원 − 스폰된 수 + 보드 위 생존 수), `prepare` 중에는 **다음 웨이브 총원**. `victory`/`defeat`에서는 0으로 덮어쓴다.
- '웨이브 시작' 버튼은 `prepare`에서만 보이고 `paused`면 비활성화.

**DOM z-order** — 드래그 고스트 10 < 나이트 쿨다운 라벨 11 < 툴팁 15 < 배너/결과 화면 20. `#banner-root`는 `pointer-events:none`이라 배너가 드래그를 가로채지 않고, **결과 오버레이만** `pointer-events:auto`로 되살린다.

### 8.2 렌더

**한 프레임의 그리기 순서**

```
보드 → 하이라이트 채움 → 라인 → 아군 기물 → 합성 미리보기 → 적(y 오름차순) → 보스 비네트 → 이펙트
```

**합성 미리보기는 기물 위·적 아래**에 그린다 — 대상 기물을 덮어야 읽히고 적은 가리면 안 되기 때문이다.

| 항목 | 값 |
|---|---|
| 칸 색 | 밝은 `#F0D9B5` / 어두운 `#B58863` |
| 좌표 라벨 | **그리지 않는다** |
| 아군 스프라이트 | 화이트 세트 72px |
| 적 스프라이트 | 블랙 세트 44px (일반=폰 / 보스=킹) |
| 티어 링 (캔버스) | 반지름 38px, 어두운 5px 바깥선 + 2.5px 색선, **스프라이트 아래** |
| 8랭크 표식 | 명도 오버레이 `rgba(0,0,0,0.14)` + 7랭크 경계 4px `#C83C32` |
| 보스 비네트 | y ≥ 480px, 그라디언트 288 → 460.8px, 알파 0 → 0.35 |

**하이라이트 색은 7종이고, 소유 위치가 두 곳이다.**

| 색 | 용도 | 소유 |
|---|---|---|
| `rgba(235,97,80,0.5)` | 사거리 | `HIGHLIGHT_COLORS.range` |
| `rgba(90,200,90,0.40)` | 나이트 이동 | `.move` |
| `rgba(0,159,217,0.5)` | 퀸 라인 | `.queenLine` |
| `rgba(255,255,255,0.25)` | 기준 칸 | `.origin` |
| `rgba(255,255,0,0.5)` | 선택 | `.selected` |
| `rgba(214,51,132,0.55)` | 합성 대상 | `.merge` |
| **`rgba(220,50,40,0.28)`** | **보스 스폰 파일 전체 강조 1초** | **`main.ts:122-126`이 직접 push** |

> ⚠️ 일곱 번째 색만 `HIGHLIGHT_COLORS` 밖에 있다. §10.4의 "표현 상수는 표현 계층이 소유한다"는 지켜지지만 **단일 출처는 아니다** — 팔레트를 손볼 때 `main.ts`도 함께 봐야 한다.

**캔버스 밖 강화 단계 표시도 둘 있다.**

- **트레이 슬롯** — 같은 `tierRingColor`를 `box-shadow: inset 0 0 0 2px`로 DOM 칸에 그린다(`slots.ts:21-22`). `border`가 아니라 `inset`인 이유는 border가 `.slot-cell`(content-box)의 칸 크기를 바꿔 그리드를 밀기 때문이다.
- **툴팁** — 이름 옆에 티어 색 `T{n}` 태그를 붙인다(`tooltip.ts:44`).

> **왜 8랭크 표식을 붉은 틴트에서 명도 오버레이 + 경계선으로 바꿨는가** — 따뜻한 나무톤 보드로 교체한 뒤 '붉은 기 위의 붉은 기'가 되어 색상 대비가 사라졌다. **손실이 색상 축에서만 났으므로 명도 축으로 대비를 만들고** 경계선을 더해 이중 표식했다.

> **왜 티어 링이 원인가** — 칸 경계에 맞춘 사각형은 인접 칸의 링과 맞닿아 어느 쪽 것인지 구분되지 않고 8랭크 경계선과도 붙는다. 어두운 바깥선을 먼저 까는 이유는 **T5 노랑이 선택 하이라이트·퀸 배지와, T6 빨강이 스폰 경계선과 색이 가깝기** 때문이다.

> **왜 T1에는 링을 그리지 않는가** — 보드 위 **모든** 기물에 상시 테두리가 붙으면 선택(노랑)·이동(초록)·사거리(주황) 하이라이트와 매 프레임 경쟁하면서 정작 "이 기물은 강화됐다"는 신호가 묻힌다. 팔레트에 흰색은 남겨 두되 그리지 않는 규칙을 `tierRingColor` 하나가 강제한다.

**스프라이트** — SVG를 로드 시점에 목표 크기로 오프스크린 캔버스에 **한 번 굽고** 이후에는 1:1로만 그린다(rasterize once, blit many). 스프라이트가 없거나 굽지 못했으면 **유니코드 글리프 폴백**으로 자동 전환한다.

**안전장치** — `render()`는 `view.shake`만큼 translate한 뒤 본문 전체를 `try/finally`로 감싸 `restore`를 보장한다.

> **왜 자체 `try/finally`인가** — 루프가 예외에서 살아남게 된 뒤로는 같은 지점에서 **매 프레임 반복 throw**가 가능해졌고, `restore`가 스킵되면 save 스택이 무한히 쌓이고 shake translate가 누적돼 **보드가 화면 밖으로 서서히 밀려난다.**

### 8.3 이펙트

8종이며 **`GameEvent` 스트림만 소비하고 `GameState`를 읽지도 쓰지도 않는다** — 데미지·처치 판정에 절대 관여하지 않는다.

| 이펙트 | 수명 | 트리거 | 용도 |
|---|---:|---|---|
| `shock` | 0.10s | `attack`(pawn) | 폰 — 회백 충격파 (대상 칸마다 1개) |
| `crack` | 0.25s | `attack`(rook) | 룩 — 갈색 균열 |
| `puff` | 0.25s | **`enemyDied`** | **처치 연출 — 회색 `#999` 원이 0 → 14px로 퍼진다** (후반 웨이브에서 가장 자주 발생) |
| `beam` | 0.30s | `attack`(bishop) | 비숍 — 흰-금 광선 |
| `explosion` | 0.35s | `knightBlast` | 나이트 — 방사형 폭발 (반지름 10 → 122px) |
| `mergeBurst` | 0.45s | `merged` | 합성 — 결과 티어 색 링 (16 → 46px) |
| `ember` | 0.50s | `knightBlast` | 나이트 잔불 14개 |
| `coin` | 0.90s | `goldGained` | 30px 떠오르는 "+NG" |

- 관통 기물(룩/비숍)의 선은 **방향별로 가장 먼 대상 칸까지 한 개씩만** 그린다.
- 화면 진동은 룩 균열 0.15, 나이트 폭발 0.25에서 시작해 **초당 1씩 선형 감쇠**한다.
- 이펙트는 `render()` 바깥에서 **같은 shake 오프셋으로 다시 translate한 뒤** 그린다 — 보드와 함께 흔들려야 하기 때문이다.

> **왜 `coin`만 0.9초로 긴가** — 광선(0.3초)이 사라진 뒤에도 "번 돈"이 잠깐 남아야 플레이어가 **비숍이 한 일을 눈으로 따라갈 수 있다.** 알파를 선형이 아니라 마지막 30% 구간에서만 떨어뜨리는 것도 숫자를 읽을 시간을 주기 위해서다.

> **왜 `update(dt)`가 0이면 아무것도 안 하는가** — 일시정지 중에도 rAF는 돌기 때문에, 감쇠와 난수 재추첨을 계속하면 **"보드는 얼어 있는데 화면만 영원히 떨리는"** 상태가 된다. 그 책임을 호출부가 아니라 shake를 소유·감쇠시키는 `Effects` 안에 둬야 다른 호출부가 가드를 재구현하지 않는다.

**배너는 두 종류뿐이다** — 보스 웨이브 준비 시작의 `⚠ BOSS WAVE`, 실제 스폰의 `♚ 보스 등장 — {파일}파일!`. 2.6초(2초 표시 + 0.6초 페이드) 뒤 DOM에서 제거된다.

### 8.4 오디오

효과음 15종 = 공격 4 + 코어 7 + UI 4. Kenney CC0 `.ogg` 15개와 1:1 대응.

**"무엇을 재생할지 결정"(`cues.ts`)과 "실제 재생"(`player.ts`)을 분리하고 `AudioController`가 잇는다.**

> **왜 분리했는가** — `highlights.ts`를 `renderer.ts`에서 떼어낸 것과 같다. `cues.ts`만 보면 **DOM·Web Audio 없이** "무엇이 울리는가"를 전부 검증할 수 있다.

**큐 트리거 경로 셋** — `GameEvent` / `state.phase` 전환(victory·defeat) / UI 제스처(`resolveUi` — core에 대응 이벤트가 없다).

**소리 3단 방어**

1. 프레임 내 **코일레싱** (같은 큐 Set으로 1회)
2. 큐별 **최소 간격 스로틀** (`enemyDied` 100ms / `pawn` 120ms / 나머지 13종 200ms)
3. **보이스 상한 8** — 재생 중인 소리는 끊지 않고 **최신 요청을 버린다**

> **왜 최신 요청을 버리는가** — 재생 중인 소리를 `stop()`하면 뚝 끊기는 게 코일레싱·스로틀보다 **더 귀에 거슬린다.**

| 튜닝 | 값 |
|---|---|
| 마스터 게인 | 0.8 |
| 피치 변주 | ±5% (같은 짧은 샘플의 반복이 기관총처럼 들리는 것 방지) |
| 음소거 램프 | 0.05초 (계단식 전환의 클릭음 방지) |
| 컴프레서 | Web Audio 기본값 그대로 — **클리핑 안전판으로만** |

> ⚠️ **음소거는 마스터 게인만 0으로 램프한다**(`player.ts:119-127`). 큐 결정·스로틀·`startVoice`는 그대로 진행되므로 **무음 상태에서도 보이스 상한 8이 정상적으로 소비되고 스로틀 상태도 갱신된다.** 음소거는 "소리를 끄는" 것이지 "오디오 파이프라인을 끄는" 것이 아니다.

**무음으로 확정된 것** — `goldGained`(같은 프레임 `attack`과 겹치므로), `merged`(전용 에셋 없음 + 화면이 이미 알림), 집기/선택 시작(v1.4에서 큐 자체 제거), 슬롯 내 재정렬.

**방어적 규칙들**

- `AudioContext`는 **첫 `pointerdown`에서** 생성·재개한다(자동재생 정책). 이 호출이 없어도 게임은 에러 없이 조용히 동작한다.
- **`'running'`이 아니면 소스를 아예 만들지 않는다** — `suspended`에서 `start()`한 소리는 `onended`가 오지 않아 **보이스 상한을 영구 소진**시키고 resume 시 한꺼번에 터진다(헤드리스 크롬 실측).
- 디코드 실패는 **큐별로 1회만** 로그하고 이후 재시도 자체를 하지 않는다(재시도 스톰 방지 — `failedLogged`가 로그 래치와 시도 래치를 겸한다).
- **시계는 항상 호출부가 주입한다** — `cues.ts`는 `performance.now()`를 직접 부르지 않아 테스트가 시간을 결정론적으로 움직일 수 있다.
- 일시정지 중에는 이벤트 경로 큐를 전혀 내지 않고 스로틀 상태도 건드리지 않지만, **phase 전환 감지는 계속한다.**

`prepareStarted`(보스 웨이브)와 `bossSpawned`는 **같은 `bossSpawn` 큐를 공유**해 10초 간격 2단계 경고를 이룬다 — 두 단계를 소리로는 구분할 수 없다(의도된 설계).

### 9.2 골드당 성능

| 기물 | 비용 | DPS (단일 칸) | 커버 칸 | 100G당 DPS | 비고 |
|---|---:|---:|---|---:|---|
| 폰 | 100G | 4.00 | 2 (전방 대각) | **4.00** | 적 1마리당 총딜은 12에 그친다 |
| 나이트 | 300G | *조작 빈도에 비례* | 최대 9 (3×3) | 아래 참조 | |
| 비숍 | 200G | 0.33 (+ 최대 3.33 G/s) | 최대 14 (대각) | 0.17 | 한 판 수입 1,120~1,850G |
| 룩 | 500G | 1.67 | **15** (파일+랭크) | 0.33 | |
| 퀸 | 900G | — (버프 전용) | 라인 22~28 | 아래 참조 | |

**나이트 — "정의 불가"는 dps에만 해당한다.** 확정 계산값은 이것이다.

```
1회 폭발 = 3 × 2^(tier−1) × (1 + 퀸버프) 피해를, 자기 칸 포함 최대 9칸에 동시
미지수는 플레이어의 조작 빈도 하나뿐이다.
```

조작 빈도 f(회/초)일 때 단일 칸 dps = 3f이고, 골드당으로는 `3f / 300 = f/100`. **룩의 0.33/100G와 같아지는 지점이 f = 1/3 — 3초에 한 번 폭발시키면 룩과 정확히 동률**이고, 그보다 빨리 조작하면 룩보다 골드당 화력이 높다. 대신 커버는 9칸으로 룩의 15칸보다 좁고 지속 압박이 아니라 단발이다. **나이트 재조정의 기준선은 이 손익분기 3초다.**

**퀸 — 손익분기는 라인 위 룩 2기다.**

T1 퀸은 라인 위 아군 각각의 기본 공격력을 ×2로 만든다. 즉 라인에 T1 룩이 k기 있으면 **추가 dps = k × 1.67**. 900G를 쓴다.

| 대안 | 추가 dps | 골드 | 100G당 |
|---|---:|---:|---:|
| 룩 1기 더 사기 | 1.67 | 500G | 0.33 |
| 퀸 (라인 위 룩 k기) | 1.67k | 900G | 0.19k |

`0.19k > 0.33` → **k ≥ 1.8, 즉 룩 2기부터 퀸이 이긴다.** 라인 하나에 룩 1기뿐이면 퀸은 손해다. 커버 칸이 22~28로 넓으므로 실제로는 여러 룩을 한 번에 얹는 배치가 어렵지 않다 — §6.4의 최소 승리 빌드 18,800G 중 **10,800G(58%)가 퀸 12기**인 이유가 이것이다.

**T6 룩 = T1 룩 32기분** — 누적 투자 16,000G, 공격력 160, 판매가 8,000G. 비숍 없는 한 판 총 골드 24,702G의 **65%**에 해당한다.

## 10. 설계 원칙

이 코드베이스가 실제로 지키고 있는 규칙들이다. 앞으로의 변경은 이것들을 깨지 않는 선에서 얹어야 한다.

### 10.1 CONFIG 단일 출처 — 그리고 알려진 예외 넷

밸런스 수치는 `CONFIG` 한 곳에서만 정의되고, 파생값은 **배열이 아니라 함수**로 유도한다(`enemyHp` / `enemyCount` / `tierMultiplier` / `sellPrice`). 툴팁·시작 화면의 수치와 사거리 그림도 `CONFIG`/`patterns.ts`에서 파생시킨다.

> **왜** — 밸런스를 바꿨을 때 설명만 옛날 값으로 남는 "튜토리얼이 썩는" 방식을 **구조적으로 불가능하게** 만들기 위해서다.

**예외는 넷이고, 전부 알려져 있다** — 원칙이 예외 없이 지켜진다고 적어 두면 §12.2가 그 서술과 어긋나므로 여기 함께 적는다.

| 위치 | 하드코딩된 값 | 코드로 표현 가능한가 |
|---|---|---|
| `tooltip.ts:25` | 퀸 버프 `+100%` | **가능하다** — `tierMultiplier(p.tier)`를 부르면 된다 (§12.1-B) |
| `titleScreen.ts:53` | `공격력 ×2 버퍼` / `두 배로 올리며` | **가능하다** (§12.1-B) |
| `layout.ts:60` | 판매 슬롯 라벨 `50%` | **가능하다** — `CONFIG.economy.sellRatio` |
| `titleScreen.ts` 속성·역할·산문·범례 | 노말/불/빛/땅/오라 등 | **불가능하다** — 정당한 예외 |

즉 이 파일들이 **정당하게** 직접 소유하는 텍스트는 마지막 줄뿐이고, 위 셋은 파생시킬 수 있는데 파생시키지 않은 부채다.

### 10.2 테스트도 CONFIG에서 유도한다

**§10.1은 `src/`뿐 아니라 `tests/`에도 적용된다.** 이 저장소가 반복 적용해 온 규칙이다 — v1.6이 깨진 테스트 11건을, v1.7이 2건을 **전부 하드코딩 제거 방식으로** 고쳤고, `simulation.test.ts:258`은 「모든 밸런스 수치는 config.ts에서 유도한다(하드코딩 금지)」를 계약으로 명시한다.

**의도된 예외도 코드에 적혀 있다.**

| 예외 | 이유 |
|---|---|
| `config.test.ts` 전체 | 공식 자체를 고정하는 테스트이므로 리터럴이 정답이다 (`enemyHp(11) === 23` 등) |
| `simulation.test.ts:125` `expect(totalEnemies).toBe(452)` | config 유도치와 **별도로** 스펙 표기가 맞는지 교차검증하는 의도적 하드코딩. 재조정 시 이 줄만 깨지는 게 정상 |

> **왜 이 원칙이 문서에 있어야 하는가** — 밸런스를 바꾸면 테스트가 깨진다. 그때 "숫자를 새 값으로 바꿀 것인가, 유도식으로 바꿀 것인가"의 답이 이 절이다. 답은 후자이고, 예외는 위 둘뿐이다.

### 10.3 미리보기 = 실제 규칙 (착지 규칙에 한해)

실제 규칙과 미리보기가 **반드시 같은 함수 하나**(`resolveLanding`)만 호출한다. 미리보기 쪽 `allowMerge`도 같은 사실(드래그 여부)에서 유도한다. **계약이 덮지 않는 범위는 §7.3에 명시했다** — `interactable()` 게이트는 미리보기가 보지 않는다.

### 10.4 core → render/ui 단방향

- 코어는 `GameEvent` 배열로만 바깥에 알린다. 이벤트는 `banners → fx → audio` 순으로 **모든 소비자가 읽은 뒤 `main`이 프레임 끝에서 한 번만 비운다** — 소비자는 자기가 읽은 이벤트를 지우지 않는다.
- 이펙트는 `GameEvent`만 소비하고 `GameState`를 읽지도 쓰지도 않는다.
- `Interaction` 타입이 `ui/`가 아니라 `types.ts`에 있는 이유: `ui/drag.ts`에 두면 `render/`가 `ui/`의 타입에 의존하는 동시에 `ui/`도 `render/`에 의존하는 **역방향 계층 구조**가 된다.

### 10.5 표현 상수는 표현 계층이 소유한다

`SPAWN_BORDER_PX` · `HIGHLIGHT_COLORS` · `TIER_COLORS` · `AUDIO_TUNING`은 `config.ts`가 아니라 각 표현 파일이 소유한다.

> **왜** — 밸런스 값과 표현 값을 한 표에 섞지 않기 위해서다. 대신 테스트가 리터럴을 못박아 회귀를 잡을 수 있도록 `export`한다.

> ⚠️ 하이라이트 색만은 **소유 위치가 두 곳**이다 — 보스 스폰 파일 강조색이 `main.ts:122-126`에 직접 박혀 있다(§8.2).

### 10.6 불변식은 함수 하나에 가둔다

| 불변식 | 유일한 근거지 |
|---|---|
| 착지 판정 (한 칸 1기물, 8랭크 금지, 나이트 제약, 합성 조건) | `resolveLanding` |
| 합성 커밋 | `commitMerge` |
| 맞교환 | `moveOnBoard` |
| 적의 현재 칸 | `enemySquare` |
| 랭크 → 픽셀 | `rankToTopY` |
| 퀸 버프가 골드에 적용되지 않음 | `pieceGold` |
| **퀸 버프의 크기 (`+= 2^(tier−1)`)** | **`buff.ts:22`** — `CONFIG`에 조정 노브가 없다 |
| T1에 링을 그리지 않음 | `tierRingColor` |
| 티어 색 팔레트 | `render/tiers.ts` |

> ⚠️ **조작 가능 조건만은 이 원칙 밖에 있다** — 같은 규칙이 `interactable()`·`canBuy`·`sellPiece` 세 곳에 따로 적혀 있다(§7.6).

### 10.7 루프는 절대 죽지 않는다

- `frame()` 본문 전체를 `try`로 감싸고 **다음 rAF 예약은 반드시 `finally`에서** 한다. rAF는 1회성이라 예약이 함수 끝 한 줄뿐이면 그 앞의 어떤 예외도 루프를 **영구히** 멈춘다(캔버스가 얼고 새로고침 외 복구 불가).
- 이전 프레임 시각(`last`)은 `tick()` **호출 전에** 갱신한다 — 예외 시 다음 프레임 `dt`가 두 번 누적돼 "멈춤 후 급가속"이 나는 것을 막는다.
- 예외는 **조용히 삼키지 않되** 5초 스로틀로 로그하고 그 사이 억제된 건수를 함께 적는다(60Hz 반복 결함이 콘솔을 채우지 않게).
- 에셋 로드 실패(SVG·사운드)는 게임을 멈추지 않고 **최소 한 번 로그한 뒤** 글리프 폴백/무음으로 남는다 — 조용히 삼키면 프로덕션 404와 "아직 로딩 중"을 구분할 수 없다.
- 매 프레임 `ViewState`는 `createFrameView()`로 새로 만들고, `EMPTY_VIEW`와 그 내부 배열/객체는 `freeze`돼 있다.

> **`freeze`의 근거는 실제 버그다** — 과거 `main.ts`가 `highlights`만 새로 할당하고 `lines`/`shake`는 `EMPTY_VIEW`와 참조를 공유한 버그가 있었다. `freeze`는 같은 실수를 개발 중 즉시 TypeError로 드러낸다.

### 10.8 일시정지 게이팅의 이중 책임

`stepGame`은 `paused`면 통째로 멈춘다. 반면 **렌더·배너·이펙트는 `realDt` 기반이라 별도로 `paused`를 확인해 멈춘다.**

> ⚠️ **새 연출을 추가할 때 이 게이팅을 빠뜨리면** 게임은 얼어 있는데 연출만 흐르는 상태가 된다.

### 10.9 되돌릴 수 있게 남겨 둔다

나이트 이동 쿨다운을 0으로 만들었지만 게이트 코드(`canLandAt` / `tryKnightBlast` / `drag.ts`)를 전부 남겨 두었다. `interval`을 3.0 등으로 되돌리면 **코드 변경 없이** 옛 동작이 복원되고, 툴팁·시작 화면 문구도 자동으로 따라 복원된다.

## 12. 알려진 한계·미결

### 12.1 실제 버그 — 둘 다 "표시 ≠ 실제"다

두 버그는 형태가 같다. **UI가 `tier`를 반영하지 않아 T2 이상 기물에서 거짓 숫자를 보여준다.** 공통 근본 원인은 §12.7에 적었다.

#### A. 판매 프리뷰가 강화 단계를 무시한다

`src/ui/drag.ts:205`가 `sellPrice(piece!.type)`를 **tier 인자 없이** 호출해 언제나 T1 가격을 띄운다.

```
drag.ts:205    sellPrice(piece!.type)          → 항상 T1 가격
tooltip.ts:46  sellPrice(p.type, p.tier)       → 정확
economy.ts:52  sellPrice(..., pieces[i].tier)  → 실제 지급액 (정확)
```

T3 룩을 판매 슬롯에 올리면 **"+250G"라고 뜨지만 실제로는 1,000G가 들어온다.** 같은 화면 안에서 두 숫자가 어긋나며, **확인창이 없어 프리뷰가 유일한 안전장치**라는 `drag.ts:198-199`의 근거를 정면으로 위반한다.

- 표시가 **적게** 나오는 방향이라 금전적 손해는 아니다.
- 근본 원인은 `sellPrice`의 `tier` 기본값이 1이라는 것 — 호출부가 빠뜨려도 **타입 오류 없이 조용히** T1 가격이 나온다.
- `'+50G'`를 단언하는 프리뷰 테스트는 `drag.test.ts:359`와 `:679` **두 곳뿐이고, 둘 다 T1 폰이다.** (`:366`과 `:380`은 판매/거부 뒤 프리뷰가 비워졌는지 보는 `toBe('')` 정리 단언이라 금액을 검증하지 않는다.) **tier > 1을 검증하는 프리뷰 테스트가 하나도 없다.**

#### B. 시작 화면의 퀸 산문만 강화 단계를 무시한다 (툴팁은 해소됨)

`recalcQueenBuffs`는 `queenBuffCount += tierMultiplier(q.tier)`이므로 **T2 퀸은 +200%, T3 퀸은 +400%, T6 퀸은 +3200%**를 준다.

| 위치 | 상태 |
|---|---|
| `tooltip.ts` | **해소됨** — `버프 효과: +${tierMultiplier(p.tier) * 100}%`로 파생되고, 겹침 규칙이 별도 행으로 붙는다. `tests/tooltip.test.ts`가 T1(+100%)·T3(+400%) 두 케이스를 고정한다 |
| `titleScreen.ts` BLURB | **남아 있음** — 역할 문구는 `공격력 배율 버퍼`로, 산문은 "합성하면 올려 주는 양 자체가 두 배가 된다"로 고쳤지만, 기준값 +100%(`두 배로 올리며`)는 여전히 코드에서 유도되지 않는다. `buff.ts`의 기준값을 바꾸면 이 문장만 따라오지 않는다 |

이 항목은 퀸 상한을 6으로 열면서 함께 정리했다(§12.8). 상한이 3이던 시점에도 T2·T3에서 이미 거짓이었으므로, 상한 변경이 만든 버그가 아니라 **v1.8부터 있던 버그를 그때 발견해 고친 것**이다.

### 12.2 문서-코드 불일치 (저장소 내부)

| 위치 | 문제 |

### 12.3 조작상의 함정

- **합성은 비가역이고 확인창이 없다.** 복구 수단은 판매(50% 손실)뿐이며, 놓기 전 유일한 사전 표시가 마젠타 칸 + 점선 링 + `T{n}` 라벨이다.
- **클릭-투-무브로도 판매가 된다.** `dropAction`이 판매 분기를 출발지 분기보다 먼저 처리하기 때문이다. "합성은 드래그 전용"이라는 제스처 분리가 **판매에는 적용되지 않는다** — 비가역 조작인데 클릭 두 번으로 성사된다.
- **같은 종류·다른 티어를 보드에서 드래그하면 조용히 맞교환이 된다** — 거부음도, 합성 미리보기도 없어서 "왜 안 합쳐지지"가 아니라 **"왜 자리가 바뀌었지"**로 보인다.
- **상한에 도달한 같은 종류 기물끼리는 드래그로 자리를 바꿀 수 없다**(`tierOverflow` 거부). 자리를 바꾸려면 클릭-투-무브를 써야 한다 — 같은 조작이 제스처에 따라 정반대다.
- **보드 위 나이트 둘은 나란히 붙어 있어도 합쳐지지 않는다** — L자 거리여야 한다(§4.4). 인접 칸 드래그는 `knightPattern` 거부다.
- **트레이 안에서는 합성이 절대 일어나지 않는다.** 슬롯 → 슬롯은 `reorderSlots`로 빠지고, 이 함수는 종류·티어를 전혀 보지 않고 인덱스만 맞바꾼다.
- **같은 칸으로 드래그하면(6px 이상 움직였다면) 거부음이 난다** — `moveOnBoard`가 제자리 이동을 false로 돌려주기 때문이다(§5.7). "아무 일도 안 일어남"이 아니라 실패 피드백이다.
- **드래그 중에는 툴팁이 절대 뜨지 않는다** — 기물을 든 채로 능력치를 확인하는 조작은 불가능하다. 합성 대상 위에서는 사거리 확인도 할 수 없다.
- **거부 사유 6종이 소리로 구분되지 않는다** — 전부 `uiInvalid` 하나다.
- **보드에 좌표 라벨이 없다.** 배너는 "♚ 보스 등장 — d파일!"처럼 파일 문자를 쓰지만, 플레이어가 그 파일이 어디인지 아는 수단은 **직후 1초간의 붉은 파일 강조뿐이다.**
- **드롭 대상 판정이 판매 슬롯을 가장 먼저 검사한다.** 판매 슬롯이 보드나 트레이와 화면상 겹치면 겹친 영역 전체가 판매로 먹히고, 판매에는 확인창이 없다 — **레이아웃 변경 시 이 우선순위가 안전 문제가 된다.**
- **`victory`/`defeat`에서도 미리보기와 판매 프리뷰가 계속 뜬다** — 실제로는 전부 거부된다(§7.3).

### 12.4 휴면 상태인 코드

**나이트 쿨다운 게이트 전체가 죽은 코드다.** `CONFIG.pieces.knight.interval`이 0이라 `cooldown`이 항상 0이고, 따라서 `drag.ts`의 집기 거부·`resolveLanding`의 `knightCooldown` 거부·나이트 합성의 점유자 쿨다운 검사가 **모두 항상 통과한다.** 관련 테스트는 `cooldown`을 수동으로 세팅해 검증한다. **`interval`을 되돌리는 순간 코드 변경 없이 전부 실전화된다.**

`Landing`의 `self` 케이스도 도달 불가 방어 코드다(§5.7) — 다만 이쪽은 되살릴 계획이 있는 게 아니라, 상위 가드(`moveOnBoard`의 `sameSquare` 조기 반환)가 먼저 걸리기 때문이다.

### 12.6 배속·시간 관련 비대칭

- **배속 2x는 게임 시간만 2배로 만든다.** 배너·이펙트 지속시간(realDt 기준)은 그대로라 **2배속에서는 연출이 게임 시간 기준으로 절반만 지속된다.**
- **오디오 스로틀은 벽시계 기준이라 배속과 무관하다.** 폰이 스로틀을 채울 만큼 모이면(대략 1배속 5마리, 2배속 3마리) 폰 레이어는 1·2배속에서 사실상 똑같이 들리고, **공격 간격 3초인 비숍/룩만 정확히 2배로 울려 후반·2배속 믹스가 비숍/룩 쪽으로 기운다.**
- 나이트 쿨다운 라벨의 800ms 타이머는 **벽시계 기준**이라 일시정지·배속의 영향을 받지 않는다.
- `effects.update(0)`은 이펙트 수명도 함께 멈춘다 — **일시정지 중에는 화면의 폭발·광선이 그 상태로 얼어붙는다**(사라지지 않는다).
- **음소거는 소리만 끄고 오디오 파이프라인은 그대로 돈다** — 무음 중에도 보이스 상한 8이 소비된다(§8.4).
- 음소거 상태는 **메모리에만** 있고 '다시 시작'이 `location.reload()`이므로 판이 바뀔 때마다 초기화된다.

### 12.7 검증되지 않은 것

- ⚠️ **`tier ≥ 2` 기물의 DOM 표시를 검증하는 테스트가 하나도 없다.** `merge.test.ts`는 능력치·판매가·버프 합산을 티어별로 다 훑지만 **전부 core 함수의 반환값**이고, 표시 계층(`#sell-preview` / 툴팁 / 시작 화면)을 티어와 함께 보는 테스트는 없다. **§12.1의 두 버그가 모두 이 한 구멍에서 나왔다.** 다음 합성 관련 변경에서 같은 구멍이 반복되지 않게 하려면 여기부터 메워야 한다.
- **`victory` / `defeat` / `waveClear` / `bossSpawn` 네 큐의 파일 배정은 실제로 들어보지 못한 채 이름만으로 정한 추정치다** — 바꿀 가능성이 가장 높은 네 줄이다.
- 웨이브 20 클리어 보너스 +300G는 정상 지급되지만 **쓸 곳이 없다**(결과 화면의 '획득 골드'에는 포함된다).
- 결과 화면이 뜬 뒤에도 **rAF 루프는 영원히 계속 돈다.** `victory`/`defeat` 큐가 매 프레임 재발화하지 않는 것은 `CueResolver`가 `previousPhase`로 전환을 감지하기 때문이다.
- 드래그 고스트·쿨다운 라벨·툴팁은 `#app`이 아니라 `document.body`에 직접 붙어 있어 `createLayout`의 innerHTML 덮어쓰기로 지워지지 않는다 — **`startGame`이 한 번만 불리는 현재 구조에서만 안전하다.**

### 12.8 변경 이력 — 퀸 티어 상한 3 → 6 (커밋 `283485b` 이후, 미커밋)

## 각주 — 지적 중 그대로 반영하지 않은 것

**[1] "판매 게이트와 `interactable()`의 조건이 서로 다르다"** (§7 누락 지적) — **부분만 반영했다.** `sellPiece`는 `paused || victory || defeat`를, `interactable()`은 `!paused && (prepare || wave)`를 쓰지만, `Phase`가 정확히 4값(`prepare`/`wave`/`victory`/`defeat`)이므로 **두 조건은 현재 논리적으로 동치**다. 조건이 다르다고 적으면 사실이 아니게 되므로, §7.6에는 실제 문제인 **"같은 규칙이 세 곳에 따로 구현돼 있어 페이즈를 추가하면 갈라진다"**로 바꿔 적었다. `DragController`의 `onMove`가 `paused`에서도 계속 돈다는 지적은 그대로 반영했다.
